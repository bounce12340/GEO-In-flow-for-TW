# 历史数据升级修复

本次专项活动标识为 `traffic-quality-repair-20261022-v1`，处理引擎为 `history-repair-v1.2`。它为本次升级前已存在的真实网站提供一次历史流量复核，保留原始浏览事件、日志、采集时判定及爬虫身份核验证据。

## 入口与操作

网站管理、全局网站管理和网站设置均有“历史数据修复”入口，独立地址为 `/settings/data-repair`。完整登录且具有网站管理权限的用户可以选择网站；公开分享、API 密钥和未完成双重验证的身份不能执行修复。

首次升级提示按用户保存，关闭提示不会提交任务。全局提示在进入页面、切回窗口时检查任务通知；统计页按对应窗口的刷新规则读取，今日自动更新与历史读取规则见 [统计加速](analytics-acceleration.md)。新安装、示例网站及本次升级后新建的网站无需专项修复。任务执行记录随网站保留。

1. 选择一个或多个网站，点击“扫描历史数据”或“扫描所选网站”。
2. 后台冻结首次扫描前已经接收、仍留存的历史范围，等待该范围内已有导入批次结束，再分批准备预览。关闭页面后后台继续运行。
3. 查看修复前后 PV、全范围去重 UV、证据覆盖及限制，可查看每日结果并导出记录。
4. 核对预览后点击“确认并生效”。存在证据限制时需单独勾选确认。多网站分别确认、分别返回结果。
5. 后台完成校验后统一切换统计代次。完成通知会引导查看结果；其他已打开的报表需手动刷新。

任务可以暂停、继续、取消或在失败后重试。已生效任务提供明确的回退操作。修正已经确认的错误证据时，先回退，再在原任务中重新准备和确认；每次操作保留审计记录。

每日对比使用提交扫描时选择的**固定任务时区**。统计时区保存到账户，默认使用 Asia/Taipei；首次登录时确认国家和具体时区。已提交任务保留提交时的时区，预览和导出保留固定时区及规则版本。

## 历史证据与统计口径

保留的服务器日志 UA 可用于重新匹配爬虫。浏览事件原本不保留完整 UA，能够确定的历史自动化证据及精确关联的补充证据可以参与修复。缺少证据的浏览访客单列为证据不足；服务器请求量不能直接折算为需要扣减的浏览 PV 或 UV。

仅保留当前统计数据库的网站，可以直接扫描库内仍留存的浏览事件、质量判定及服务器日志记录，无需提供旧数据库备份。缺少原始 UA 或精确关联证据的历史记录会明确列为证据不足，并保留原有判定。补充文件为可选输入，适用于仍保留可精确关联原始证据的网站。

补充文件采用 UTF-8 JSONL，每行包含以下一种精确关联：

```json
{"eventId":"浏览采集事件的 UUID","requestUserAgent":"原请求 UA"}
{"clientEventId":"已留存接收凭证对应的 UUID","requestUserAgent":"原请求 UA"}
```

最终提交使用有序分块摘要，文件分块数量增加时，确认请求体保持固定大小。

当前候选规则包最多保留 100 个未撤下文件；历史生效及回退代次引用的来源按归档保留。每个文件最多显示 100 条固定原因的错误摘要；上传当场显示原文件行号，重新进入页面后显示分块和记录位置。

同一行只能提供一种 ID，必须对应本网站冻结范围内的浏览事件。文件不能包含原始 IP 或其他字段。页面逐行解析并以每块最多 1 MiB、1,000 条提交；UA 只在服务端内存参与识别，修复表保存分类结果和摘要。无效、冲突、未完成或缺块文件会阻止确认，管理者可以修正或撤下文件。上传中关闭页面后重新选择原文件可续传，规则变化后需要重新提供原文件。

修复结果覆盖浏览质量判定和普通爬虫统计，继续遵守现有来源仲裁、流量策略和域名过滤。自定义事件按自身证据判断，其属性和收入跟随父事件。GEO 权重 v2 继续使用原始归档身份与核验证据，历史修复不会补造已核验抓取。

扫描、准备、待确认和校验状态均不发布候选结果。所有结果通过同一次代次指针及统计修订切换生效；回退切换指针并更新统计修订。原始记录保持完整，升级后的基础质量过滤继续有效。

## 部署与运维

使用现有的一键部署流程升级应用、日志 worker 和分析 worker。新增迁移为 `034_history_repair.sql` 和 `035_history_repair_property_reads.sql`，固定队列为 `liekan-history-repair`；队列初始化脚本会创建或更新该队列。无需新增服务、部署密钥或用户环境配置。

数据库迁移只登记当时已经存在的网站，不会自动扫描或清洗。扫描前应完成采集应用与兼容 worker 升级。首次扫描冻结接收边界，覆盖滚动升级期间收到的数据；冻结后发现旧实例继续写入未标记边界，会提示范围变化并阻止候选生效，同时保留原始采集和已经生效的结果。

全局同时处理一个修复任务，各网站通过短批次排队轮转。SQL 单语句预算 5 秒，事务预算 30 秒，租约 60 秒并每 15 秒续期。任务进度读取使用持久化任务状态；页面只在可见且任务执行中每 3 秒读取状态。后台每 60 秒核对丢失或过期队列记录，取消和耗尽重试的任务需要明确操作后才能继续。

网站转移会停止原操作者未生效的任务，生效结果及回退基线随网站保留。网站清空或删除会清理关联修复数据。未确认候选及临时工作数据闲置 7 天后过期，需重新扫描；生效和回退引用的最小证据继续保留。终态临时访客集合在 7 天后清理，汇总与审计保留。

过期时立即隔离整批旧输入，后台继续分批释放存储。清理期间重新扫描也需要重新提供过期文件；未产生变更、取消或失效的任务同样清理临时明细，保留每日汇总与审计。其他有权管理者重新生成预览时，后续处理使用此次提交人的权限。修订回退任务的证据期间，可以按代次继续查看和导出此前确认的归档结果。

应用版本回退前应停止领取新修复任务，由管理员在页面明确回退已生效修复，再切换已经验证兼容的应用与 worker 组合。新增数据库迁移和审计表保留，不运行向下迁移或数据库重置。

## 验证

`pnpm test:history-repair` 使用独立 PostgreSQL 测试容器、随机业务 schema 和固定端口保护，验证迁移、边界、证据、预览确认、任务恢复、统计切换和回退。测试数据和凭据与本地业务数据库隔离，结束后只清理测试自行创建的容器。

相关回归检查包括类型、单元测试、原有流量质量和爬虫证据集成测试、部署检查、接口生成一致性、原始视觉基线与生产构建。浏览器验收使用独立浏览器上下文，以中文、英文及桌面、手机尺寸检查入口、确认和进度。

`pnpm test:history-repair -- --benchmark` 在同一隔离数据库中准备 100 万和 1,000 万条历史记录，每种规模采样 20 个真实工作单元，并同步采样采集 P95、内存、检查点和暂停行为。完整重建耗时由网站的实际留存范围和证据数量决定。


修复预览按浏览统计的当前来源、域名、Origin 与已确认排除集合计算影响。治理修订变化后，待确认预览需要重新生成。缺少事件身份快照的历史浏览量仍可参与 PV；UV 总数显示不可用，已确认身份的 UV 和缺失身份的 PV 单列记录。旧代次没有身份覆盖证明时继续保持未知，原始判定和已发布代次保留。

迁移会失效尚未完成的旧引擎候选与工作租约，保留已生效和回滚代次。数据库拒绝旧引擎继续创建或推进任务。部署应同时更新应用和 worker，并停止旧 worker，随后重新生成需要继续的预览。旧操作收据保持原样；重试响应按当前身份可用性规则展示。
